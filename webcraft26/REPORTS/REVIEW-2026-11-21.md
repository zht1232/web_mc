| # | 问题 | 结论 | 级别 |
|---|---|---|---|

### 1.2 启动链

`index.html` → `src/main.ts`：
1. 创建加载屏（Mojang 标志 + 进度条）。
2. `new Game(app, seed, workers)`，注册 `onStatus` 进度。
3. `await game.init()`：
   - 加载区块数据/启动 chunk worker；
   - 加载模型/纹理/字体/GUI 资源；
   - 准备世界生成器 → `ClientLevel`；
   - 创建 `LevelRenderer` → `SurvivalState` → `ItemIconAtlas` → 实体渲染器 → 天空/云/天气/粒子/手；
   - 等待出生区生成、放置玩家、创建 `EntityManager`；
   - 打开存档、加载语言、创建 `ScreenManager`；
   - 根据 `?play` 进入世界或标题屏。
4. `game.start()` 启动 rAF 循环；`window.__mc = game` 供测试/探针使用。

## 2. 玩法 / 交互

### 2.1 掉落物：渲染是占位（P0，已确认）

**现象**：掉落物只显示一粒小像素方格。

**证据**
- `src/client/renderer/entity/ItemEntityRenderer.ts:1-34`：
  - 注释明确“deliberately not used... solid colour derived from item id”；
  - `getModel()` 返回 `ItemCubeModel`，`getTextureKey()` 返回白色纹理；
  - `getTint()` 用物品名哈希生成 RGB，完全不使用物品贴图/模型。
- `src/client/renderer/entity/model/EntityModels.ts:875`：
  - `ItemCubeModel = singleBoxModel(-2, 20, -2, 4, 4, 4, ...)`：4x4x4 **像素**的方块；
  - 放在 `y=20`（实体原点上方），没有居中。
- `src/vanilla/world/entity/item/ItemEntity.ts:25`：`this.scale = 0.4`。
  - 4px × 0.4 / 16 ≈ **0.1 格**（10cm），所以看起来就是一个小方格。
- `ItemEntity.bob/spin`（`ItemEntity.ts:18-19,46-47`）在渲染器里没有使用；没有浮动、旋转、堆叠数、物品模型。

**原版/Horizon**
- 原版 `ItemEntityRenderer` 用物品模型（block item 用 3D 模型，flat item 用图标），有 `bob`、自转、堆叠数、阴影；渲染尺寸约 0.25 格。
- Horizon 的 `render_slots.rs`/`item` 渲染路径使用物品模型与图标，不是实心立方体。

**修复方向**
1. 复用 `ItemIconAtlas` 的 3D 烘焙结果或直接复用 block/item 模型，渲染真实物品；
2. 使用 `bob/spin` 做上下浮动与 Y 轴旋转；
3. 在 `ItemEntityRenderer` 中按 `stack.count` 绘制数量（可直接复用 HUD 的 `drawItemCount`）；
4. 修正 `ItemCubeModel` 的居中/尺寸（若保留兜底 cube）。

### 2.2 物品栏鼠标移动、放下后光标悬浮（P0，已确认）

**现象**
- 物品栏里用鼠标移动方块逻辑不对；
- 放下一个方块后，光标上还悬浮着那个方块；
- 创造模式无法调整装备。

**证据**
- 创造物品栏的格子点击在 `CreativeModeInventoryScreen.ts:200-239` **自己处理并提前 return**：
  - `down` 命中物品格 → `this.menu.click(idx, button, shift, 'PICKUP'/'CLONE')` → `return true`；
  - 没有设置父类 `AbstractContainerScreen` 的 `pressedSlot`，也没有设置 `containerDragButton`。
- 父类 `AbstractContainerScreen.ts:366-439` 的放下逻辑依赖这两个状态：
  - `up` 且 `containerDragButton < 0 && pressedSlot >= 0` 才走“按下 A、抬起 B”的 PICKUP；
  - 普通 `up` 且 `containerDragButton >= 0` 才走 quick-craft/PICKUP。
  - 创造格子的 down 把状态绕过去了，抬起在热栏时两个条件都不成立 → **carried 不会被放进槽位**，于是光标继续悬浮。
- `Game.ts:974-1054` 的 `containerAdapter()` 为创造模式另写了一套：
  - `isCreative()` 只看当前 screen 是否是 `CreativeModeInventoryScreen`；
  - 格子 0..44 是虚拟 `creativeGrid`，`canPlaceItem` 直接返回 false；
  - `QUICK_MOVE` 在格子上是“复制到光标”，`SWAP` 是“把物品写到热栏并 copyWithCount(max)”，与 vanilla 的 shift-click/数字键语义不同。
- 创造物品栏 `buildSlots()`（`CreativeModeInventoryScreen.ts:105-117`）只有：
  - 45 个物品格；
  - 9 个热栏格；
  - **没有**盔甲槽 5..8、副手 45、2x2 合成、玩家预览。
- `SlotLayout.ts:119-133` 的 `MENU_ARMOR_SLOT_START` 映射只被生存背包的 `InventoryMenu` 使用；创造屏没有这些 SlotDef。

**原版/Horizon**
- 原版 `AbstractContainerScreen` 的状态机：down 记录 `pressedSlot`/`doubleClick`，move 才启动 quick-craft，up 统一走 `slotClicked`；创造物品栏的格子只是“无限源”，仍然复用同一套点击语义。
- 原版创造物品栏的 Survival Inventory 页有盔甲槽、副手、2x2 合成、玩家预览和销毁槽。

**修复方向**
1. 创造格子的 down 不要提前 return：设置 `pressedSlot`，交给父类状态机；格子只作为 `canPickup=true` 的无限源。
2. `containerAdapter` 的创造分支补齐 `QUICK_MOVE`/`SWAP`/`QUICK_CRAFT` 的 vanilla 语义；不要把 `QUICK_MOVE` 简化成“复制到光标”。
3. 创造屏的 `buildSlots()` 增加盔甲/副手/合成/预览布局（可直接复用 `SlotLayout.playerInventorySlotRects`）。
4. 给 `test-containers.mjs` 增加“创造格 → 热栏拖放后 carried 为空”和“创造盔甲槽可放置”的断言（现有 19 项没有覆盖）。

**实机复现（B-02，`scripts/audit-behavior-p0.mjs`）**：
创造格 down 后 `carried={itemId:1,count:1}`；移到热栏 up 后仍是 `{itemId:1,count:1}`，热栏为 `{itemId:-1,count:0}` —— 光标上的物品没有放下。

### 2.3 “方块放完后切到那一格手上又出现方块”（P0，已确认）

**这不是创造模式无限方块，而是空栈判定漏了 `isEmpty()`。**

**证据链**
1. `ItemStack.isEmpty()`（`ItemStack.ts:50`）的判定是 `item === null || count <= 0`，`getCount()` 在空栈时返回 0（`ItemStack.ts:52`）。
2. 放置后 `Game.ts:1898` 调用 `survival.inventory.removeFromSelected(false)`；`Inventory.removeFromSelected`（`Inventory.ts:282-285`）→ `ContainerHelper.removeItem`（`Container.ts:24-29`）→ `ItemStack.split`（`ItemStack.ts:74-79`）：
   - `split` 只 `this.shrink(real)`，把 `count` 减到 0；
   - **没有把 `item` 置空，也没有把该槽替换成 `ItemStack.EMPTY`**。
3. `HandRenderer.tick()`（`HandRenderer.ts:356`）：
   ```ts
   const nextId = survival.getSelectedStack().item?.namespacedId ?? '';
   ```
   只看 `.item`，不看 `isEmpty()`。count 为 0 的栈仍然有 `item`，所以 `visibleItemId` 继续是那个方块，`render()` 继续画它。
4. `Game.renderHud` 的 `toSlot`（`Game.ts:2732-2733`）：
   ```ts
   item: s.item ? s.item.id : -1,
   ```
   同样不看 `isEmpty()`；热栏会继续显示一个数量为 0 的方块图标。

**结论**：放置最后一个方块后，库存槽是“count=0 但 item 非空”的僵尸栈；手部/HUD 都把它当有物品。切到那一格自然又“出现”方块。

**实机复现（B-01，`scripts/audit-behavior-p0.mjs`）**：
`count=0, isEmpty=true, item=true, hand=minecraft:grass_block` —— 空栈仍保留 `item`，手部仍显示草方块。

**修复方向**
1. `ContainerHelper.removeItem` / `Inventory.removeItem` 在 `split` 后如果 `isEmpty()`，把槽位写成 `ItemStack.EMPTY`（或 `setItem(slot, EMPTY)`）。
2. 所有渲染/查找路径统一用 `stack.isEmpty()`：`HandRenderer`、`toSlot`、`getSelectedStack` 的消费方、物品栏 tooltip/图标绘制。
3. 增加回归测试：生存模式给 1 个方块 → 放置 → 断言槽位 `isEmpty()`、`HandRenderer.visibleItemId===''`、HUD 该格不画图标。

### 2.4 创造模式飞行手感（差异）

**证据**：`src/vanilla/world/entity/player/Player.ts:102-149`、`src/client/Game.ts:1274-1283`、`2244-2252`。

| 项 | 当前实现 | 原版/Horizon | 影响 |
|---|---|---|---|
| 水平目标速度 | fly 0.5395、fly-sprint 1.079 | 与 vanilla 量级一致 | 上限没问题 |
| 水平加速 | 由 `damping=0.91` 反推 `accel` | vanilla 用 `flyingSpeed` 加速 | 起步/转向可能偏“黏” |
| 垂直 | `vy = ±SPEED.fly` **瞬时赋值**；松开后 `vy *= 0.85` | vanilla 有加速/阻尼过程 | 上下飞“很硬”，没有惯性 |
| 双击 | 280ms | vanilla 约 250ms | 触发窗口偏长 |
| 额外键 | `KeyF` 切换飞行 | 原版只有双击空格 | 额外行为，可保留但要在设置里说明 |
| 冲刺 | `input.forward <= 0` 立刻取消 sprint；飞行的 `|| this.flying` 分支被下一行抵消 | 悬停时不冲刺 | 飞行冲刺手感不一致 |

**建议**：先做 A/B 数值探针（同一位置、同一输入序列采样速度曲线），再决定是改垂直加速/阻尼还是只改双击阈值；不要直接照抄一个数字。

## 3. 实体 / 模型

### 3.1 动物/怪物“仇恨”与一直跟随（P0，已确认）

**证据链**
1. `Animal.registerGoals()`（`Animal.ts:17-25`）注册 `TemptGoal`；`TemptGoal.canUse()`（`TemptGoal.ts:19-28`）注释直接写：
   > “The item check is simplified to ‘player within range’”
   - 只检查玩家存活 + 距离 ≤ 10 + 1/3 随机，**完全不检查手持食物**；
   - 命中后 `tick()` 每 tick `setWantedPosition(player)`，所以所有动物会无条件跟着玩家。
2. `LookAtPlayerGoal`（`LookAtPlayerGoal.ts:14,19-27`）默认 `chance = 0.5`；原版默认是 **0.02**。所有注册该 goal 的生物（Monster 和 Animal 都有）会高频盯着玩家。
3. `Monster.registerGoals()`（`Monster.ts:16-24`）给所有怪物加 `NearestAttackableTargetGoal(this, range, this.playerPredicate)`；`playerPredicate` 只判断 `getTypeName() === 'player'`（`Mob.ts:99`），**没有创造/旁观过滤**。
4. `NearestAttackableTargetGoal.canUse()`（`NearestAttackableTargetGoal.ts:22-41`）只检查 `isAlive()` 和 predicate；创造模式玩家仍会被选为目标。
5. `CreeperSwellGoal`（`CreeperSwellGoal.ts:16-46`）只要求目标存活 + 距离 < 9；`Creeper.explode()`（`Creeper.ts:27-45`）无模式判断；`Game.explode()`（`Game.ts:1692-1718`）无条件破坏方块并对玩家 `survival.damage(...)`。

**结论**
- 动物“跟随”不是仇恨，是 `TemptGoal` 桩；怪物“跟着”是目标选择；两者叠加让所有生物都像对玩家有仇恨。
- 苦力怕在创造模式爆炸是上述链路 + 无创造判定的直接结果。

**修复方向**
1. `TemptGoal` 必须检查玩家主手/副手是否在 tempt items（小麦/种子/胡萝卜等，按 `Animal` 子类配置）。
2. `LookAtPlayerGoal` 概率恢复到 0.02（或按 vanilla 构造函数默认值），并只对配置了该 goal 的生物生效。
3. `NearestAttackableTargetGoal` 增加 `Player.isCreative()`/`isSpectator()` 过滤（或按 vanilla `TargetingConditions`）。
4. `CreeperSwellGoal`/`Creeper.explode` 增加创造、难度、`mobGriefing` 判定；`Game.explode` 对创造玩家不造成伤害。
5. 增加回归测试：创造模式玩家 5 格内放僵尸/苦力怕，10 秒内不得设目标、不得膨胀/爆炸；动物不持食物时不得跟随。

**实机复现（B-03，`scripts/audit-behavior-p0.mjs`）**：
创造模式玩家旁边召唤僵尸/苦力怕 2.2 秒后，`zombieTarget=player`；苦力怕暂未选目标但代码路径同样无创造过滤。

### 3.2 羊的羊毛层尺寸（P1，已确认）

**证据**

### 3.3 骷髅弓 / 生物手持物（P0，已确认）

**证据**
- `EntityModels.ts:256-323`：`SkeletonModel` 把弓作为 `right_arm` 的子节点内置：
  - 3 段弓身 + 4 段弦，全部用 `BOW_WOOD/BOW_STRING` tint；
  - 弓的位置/旋转写死在手臂骨骼里。
- `EntityRenderer.ts:297-300`：
  ```ts
  // This port has no mob equipment, and the skeleton is our only ranged attacker,
  // so it is always rendered in the bow pose.
  ctx.isHoldingBow = e.getTypeName() === 'skeleton';
  ```
  - 骷髅**永远**是 BOW_AND_ARROW 姿势，无论实际是否持弓/是否近战。

**修复方向**
1. 给 `Mob`/`LivingEntity` 增加 `equipment`（主手/副手/头盔/胸甲/腿甲/靴子）与 `getMainHandItem()`；
2. `EntityRenderer` 增加 `getHandLayers(e)`，按 hand bone 矩阵渲染物品模型（复用 `HandRenderer`/`ItemIconAtlas` 的模型烘焙）；
3. `ctx.isHoldingBow` 改为“主手物品是 bow”，并支持近战/空手姿势；
4. 删除 `SkeletonModel` 内置弓（或只在没有装备层时作为兜底），让弓来自物品层。

## 4. 渲染 / 光照 / 天空

### 4.1 傍晚天空分界线（P1，已确认）

**代码事实（2026-11-21 复核后更正）**
- 天空 pass：`SkyRenderer.render()`（`SkyRenderer.ts:426-451`）调用 `computeFogColor({ ..., cameraForward: forward, sunriseSunsetColorArgb: sky.sunriseColorArgb })`。
- 地形雾：`LevelRenderer.ts:1089-1107` 的 `computeFog({ ... })` **确实传了 `cameraForward`、`sunriseSunsetColorArgb`、`rainLevel`、`skyLightLevel`**；所以“地形雾永远不混 sunrise”的旧结论是**错的**，已删除。
- 真正剩下的不一致：
  - GL clear：`Game.ts:2596` 用 `skyState.fogColor`（原始 fog），不是 `computeFogColor` 的 view-dependent 结果；
  - 天空圆盘：`SkyRenderer.ts:92-93` 在 `dist > 512` 直接 `discard`，近地平线的天空可能露出 clear 色；
  - 天空圆盘只覆盖 `dir.y > 0`，下方是否由地形/暗盘接住取决于相机高度。
- 结论：天空与地形雾大体已同期；**分界线更可能出现在近地平线的 sky-disc 裁边/clear 露出**，需要固定 time + 朝向的截图探针确认，而不是再归因于“地形没传 cameraForward”。

**下一步**
1. 固定 time（日落）和朝向（朝太阳/背向太阳）截图，对比 `setShaders(false)`；
2. 采样地平线上方 1-2 像素的颜色，判断是 sky disc 边缘还是 clear；
3. 修复方向：clear 改用同一个 `computeFogColor` 结果；天空 disc 不要硬 discard，改为在 `dist` 上淡出或覆盖完整上半球。

### 4.2 火把被阴影截断（P1，已确认）

**代码事实**
- `Shaders.ts:165-171`：`light = texture(uLightmap, ...)`，`color = tex.rgb * vColor.rgb * light`；这里的 `light` 是**天光+方块光合成后的结果**。
- `Shaders.ts:176-200`：阴影项
  ```glsl
  color *= mix(1.0, mix(0.55, 1.0, lit), skyMask * ndl * sunUp);
  ```
  直接乘在**整个 color** 上；只要 `skyMask>0`，火把照亮的区域也会被太阳阴影压到 0.55，出现硬阴影边界切过火把光池。
- `skyMask = smoothstep(0, 0.55, vLight.x/15)` 用的是顶点天光；火把附近如果有天光，就会触发太阳阴影项。

**修复方向**：把 lightmap 拆成“天光贡献”和“方块光贡献”，阴影只衰减天光/直射项；例如采样 `lightSky` 与 `lightBlock` 两张/两次，`final = block + sky * shadowFactor`。

### 4.3 下挖一格局部死黑（待复现）

**现状**
- `ClientLevel.setBlockState`（`ClientLevel.ts:269-282`）会调用 `light.blockChanged`，`LightEngine.blockChanged`（`LightEngine.ts:246-288`）会清 sky、重算列、传播，再 `markDirtyAround`；顺序是对的。
- `SectionMesher.smoothBlend`（`SectionMesher.ts:177-196`）实现了原版的“邻居 sky=0 时继承 center sky”规则；理论上洞底的天空光不会变成 0。
- 但 `Shaders.ts` 的阴影乘子仍会把洞底/洞壁压到 0.55；`ambientColor` 默认 `0x0A`，洞壁本身就只有 ~0.039 的环境光，再乘 0.55 会接近纯黑。

**结论**：不能仅凭代码断定是“天光没更新”；更可能是**阴影乘子 + 洞壁低环境光**叠加。建议写一个固定场景探针：
1. 平地挖 1 格，截图；
2. `setShaders(false)` 再截图（排除阴影）；
3. 打印洞底/四壁的 `getSkyLight/getBlockLight` 与顶点 `vLight`；
4. 对比原版同场景截图。

### 4.4 物品栏草方块过艳（待复现）

- `ItemIconAtlas.ts:238-247`：图标用 `TERRAIN_FRAG` 烘焙，`uUseShadows=0`、白色 lightmap、`frontLight` 仅在 `guiLight==='front'` 时为 true。
- `public/mc/itemmodels.json` 中 `grass_block` 是 `guiLight: "side"`，所以会走 `faceShade`，不是全亮。
- `itemIconTint('grass_block') = 0x91BD59`（`ItemIconAtlas.ts:466-477`）；`grass_block_top.png` 平均色 #A0A0A0；理论乘法结果 ≈ #5B7638，并不算荧光绿。
- 因此“过艳”目前**没有代码级证据**；可能是与原版图标对比时的观感、或图标烘焙时的 mip/颜色空间差异。建议截取原版 `grass_block` 图标（同 GUI scale）做逐像素对比，再决定是否调整 tint/faceShade。

### 4.5 光影 vs Complementary（P2，差异明确）

当前 `PostProcessor` 是**受 Complementary 启发的自研简化链**，不是 pack 兼容层：

| 维度 | 当前 | Complementary 级 |
|---|---|---|
| 管线 | HDR 场景 → bloom mip → 5x5 模糊 → Lottes tonemap → FXAA | 完整 gbuffer + 多 pass 合成 + 体积光/云/大气 |
| 阴影 | 2 级联、5x5 PCF、2048/4096 | 多级联、彩色阴影、软阴影、阴影失真 |
| 水 | 顶点波 + Fresnel + SSR | 折射、真实反射、波法线、水平面融合 |
| 云 | billboard/平面云 | 体积云/多层云 |
| 光 | lightmap + 单太阳衰减 | 多光源、发光方块、手部光源、环境光探针 |
| 后处理 | SSAO（深度差）、TAA（相机重投影）、bloom | SSAO/GTAO、TAA with motion vectors、自动曝光、色彩分级 |
| 色彩 | exposure 1.4、bloom 0.12、threshold 0.6 等手调 | 完整 HDR/tonemap/色彩管理 |

**建议**：如果目标是“像 Complementary”，需要把它当独立渲染项目（gbuffer/材质/多 pass），不是调几个 uniform；按用户的优先级，放在玩法之后。

### 5.1 现状

  - `Beardifier`
  - `Blender`
  - `biome zoom`
- `NoiseChunkGenerator.ts:113-130` 会加载 `thirdparty/src-vanilla/assets/minecraft/worldgen.json` 与 `tags.json`；密度函数/噪声/群系参数是数据驱动的（不是纯硬编码）。
- `FeatureGenerator.ts:12-14`：只执行 decoration steps **6–10**（矿、地下装饰、流体泉、植被、顶层修改）；**跳过 0–5**（结构、湖泊）。
- `VillageGenerator.ts:4-13`：只有程序化村庄，没有 NBT 模板/结构集；没有要塞、矿洞、废墟等。
- `WorldgenRandom.ts` 是 Xoroshiro/WorldgenRandom 的精确 port；seed 在 `NoiseChunkGenerator` 用 `bigint`。

### 5.2 “同种子能否生成一模一样的地形？”

**结论：当前不能。** 不是“加一个 seed 参数”的问题，而是生成管线还缺多个决定性阶段：

1. **P0 数值一致性**：Java long seed → 128-bit Xoroshiro、`nextLong` 符号扩展、`DensityFunction.minValue/maxValue` 短路、浮点精度；需要 golden stream 测试。
2. **P0 数据图完整性**：`noise_router` 的 `final_density`/`preliminary_surface_level`/`interpolated` 必须全部执行；任何节点简化都会改变地形。
3. **P1 缺失阶段**：carvers（洞穴/峡谷）、OreVeinifier、Beardifier、Blender、biome zoom。
4. **P1 结构与 feature**：结构步骤 0–5、湖泊、NBT 模板、结构集；当前只有村庄。
5. **P1 群系边界**：surface rules 使用原始 quart biome，原版有 biome zoom；群系边缘的地表块会不同。
6. **验证**：没有 Java 原版 chunk hash golden test；现有测试只证明“同 seed 在本项目内可重复”，不等于“与 Java 一致”。

**建议**：先做“密度函数/区块 hash 对 Java”的 golden test，再逐阶段补齐；在这之前，不要把“同 seed 同地形”作为承诺。

## 7. 音效

**事实**
- `public/mc/sounds/index.json` 有 **959 个事件**、目录下 **4341 个 ogg**；但**没有 music/record 目录**（`public/mc/sounds` 下只有 ambient/block/entity/weather/ui）。
- `SoundEvents.ts:1-6` 注释仍写“28 events/112 files”，已过时；`SOUND_ALIASES`（`SoundEvents.ts:52-78`）把 `music.game/menu/creative/nether/end` 映射到 `block.water.ambient`/`ambient.underwater.*`。
- `SoundEngine.resolveEvent`（`SoundEngine.ts:144-149`）先查真实事件，再查别名；所以大部分别名是死代码，但 **music 事件确实不在索引里**，会播放水/水下音效。
- `Game.blockMaterial`（`Game.ts:1601-1610`）是粗粒度正则：dirt/ore/deepslate 等大量方块回退到 `stone`；`blocks.json` 的 `sound` 字段能覆盖一部分，但 fallback 很粗。
- 挖掘过程中没有 `block.*.hit` 循环音效（`Game.ts` 只在 break 时播放 `.break`）。
- `MobSounds` 事件选择基本正确（`entity.<type>.ambient/hurt/death/step`），但 `hasRealEvent` 过滤后，缺失事件的生物会完全静音。

**结论**
- “音效不对”的首要原因是 **music/record 资源缺失 + 别名**，其次是方块材质映射过粗、缺 mining hit。
- 修复：补齐 music/record ogg；删除 music 别名；按 `SoundType` 表而不是正则映射方块音；在挖掘 tick 播放 hit。

## 10. 验证方案（可在不改代码的情况下先建）

1. **掉落物**：固定位置 drop 一个 `grass_block`/`iron_pickaxe`，截图；断言模型尺寸/旋转/数量。

## 13. 一句话总结

这不是“再调几个参数”的问题：**掉落物/创造物品栏/生物 AI/生物装备层是玩法层的结构性缺口，天空/火焰阴影/音效是数据与管线不一致，地形同种子一致是长期 parity 工程，光影是另一个量级。** 先按 Phase A 把玩法做对，再进入 Phase B 的视觉与世界，最后才碰 Phase C 的光影。
