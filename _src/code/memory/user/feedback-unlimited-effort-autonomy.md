当用户说“你的 token 是免费的，给我使劲工作，给你无限时间”这类话时，按**不设预算**来干活：连续推进多个里程碑、并行派 agent、做完整实测验证，不要把工作切成小块等他逐次批准，也不要用“要不要我继续？”来收尾。

**Why:** 2026-11-01 在 webcraft26（浏览器 1:1 复刻 MC 26.2）里，他连着两次强调免费 token / 无限时间 / “哪里不懂你去解包或者上网搜索”，并且明确要求“每一个细节都和原版对照”。此前我因为按默认习惯收敛范围、只做最小改动，被评价为交付“看起来像劣质游戏”。他要的是**范围和深度都拉满**，同时结论仍然要收敛成清单（见 [[user-profile]] 的“回答要短、按优先级排”）。

**How to apply:**
- 报缺陷时不要只修他点名的那几条，顺手把同一子系统里查得到的偏差一起修（例：他说手臂/阴影/湖面/移动，顺带纠正了物品栏图标几何、面光照常数、跳跃高度、方块交互距离）。
- 不确定数值时**先测量再断言**：读本地官方数据文件 > 实测 > 记忆/网络搜索。见 [[feedback-verify-claims-before-recommending]]。
- 允许长时间连续作业和多 agent 并发，但要守住 CPU/浏览器验收的瓶颈（见 [[feedback-subagents-encouraged]]）和不可逆操作确认（部署、动生产服务器、push）。
- 仍然不要为了省时间跳过验证：他要求“进游戏看效果”，未实测的改动不要当成交付。见 [[feedback-perf-and-liveliness]]。
